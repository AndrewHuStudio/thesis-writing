# 门诊平面结构化标注

逐张把门诊概念平面整理为可校订的空间与关系数据。先读原图和已有成果，沿用当前项目的稳定编号及已确认名称，按统一类别和以下文件规范交付；每张图独立判断，不套用其他医院的坐标或房间数量。

## 交付与精度

每张图最终只保留四个文件：具名原图（现有 `编号_项目名称_原图.ext` 沿用）、`标注.svg`、`annotation.json`、`标注说明.md`。SVG、JSON、MD 使用上述固定名称。处理经授权迁移的旧样本时，将 `标注预览.svg`、`spatial_data.json` 等分别统一为 `标注.svg`、`annotation.json`，更新当前材料中的有效链接；历史备份保留原样。仅处理当前用户指定医院，不因统一规范而批量改动其他医院。同院多张图分子目录。截图、PNG 检查图和脚本临时产物放临时目录，默认不输出网页、额外审核 JSON 或重复压缩包。清理用户已有文件须在其授权范围内。

## 流程

读取与备份 → 空间草稿 → 房名核对 → 同步填写 → 连通复核 → 同步门洞 → 校验与目检 → 四文件定稿。回复用简短中文：先给结果，再列待确认项；不展开无关过程。

## 名称、类别与格式统一

- JSON 的 `name` 保存原图可读或用户已确认的具体名称，`type` 使用 [space-types.json](references/space-types.json) 中的共享英文代码；标准中文类别只从同一类别表读取。财务、主任办等具体名称可共同使用 `office`，不能用医院各自的叫法生成不同类别编码，也不能从缩写补出未经确认的用途。
- SVG 可见标签统一为“稳定 S 编号＋具体名称＋〔标准功能类别〕”，与 JSON 的 `id`、`name`、`type` 对应。稳定 S 编号须实际写在对应空间轮廓内部，不能只放在图外图例或悬停标题。具体名称承载案例信息，标准类别用于跨医院比较与编码；不要为了外观一致而抹去已确认的名称。未知名称仍按未确认规则显示，不把分类推测写成具体名称。
- JSON 固定顶层 `image`、`spaces`、`relations`，UTF-8、两个空格缩进，字段遵循 [schema.md](references/schema.md)。已定位开口存于对应 `access.openings`；不添加重复的房名、类别中文、门表或过程字段。
- 后续对其他医院的补充须在用户指定的新对话中读取本 Skill，并逐张核对各自原图；固定文件名和字段结构不表示门洞及连通性已完成。

概念精度记录空间功能、范围、相对规模与可达性。**原图清晰可辨的门洞和无门开口要记录近似位置，SVG 用红点显示，并与 JSON 的人员可达关系一一对应；不能因删除施工细节而一并删除这些定位信息。**半墙服务区经图面或用户确认可达、但未画出小门时，只记录概念连接，不要求或编造门位。门宽、门扇形式、半墙缺口形状或交通核内部精确路线不纳入数据。交通核可按整体节点保存。服务窗口、共墙与人员可达分别记录。按图明确范围，不把急诊、住院支持和普通门诊无说明混同。

## 连通复核：先自主判断，再问关键疑点

默认服务于概念级空间布局研究，优先确定主要功能空间、走廊／大厅、交通核和建筑入口之间的可达关系。沿用已有空间层级、稳定 S 编号与用户确认；局部复核不继续细分功能区内部的小房间，也不要求穷尽每个小间的开门和内部连接。

提交核对材料前，先回看本图布局，将疑点分为以下三类：

- **可以自行判断：**图面连续、可见开口，或结合出入口朝向、相邻通道及完整通行组织能形成有依据的概念连接时，由助手完成判断。需要合理推断时，在外部核对记录简述空间对及依据，写明“布局推断”，不写成用户已确认。不能只凭共墙、服务窗口或“通常医院都会这样”建立 `access`。
- **本轮无需细究：**小设备间、管井／检修空间、辅助小间内部路线、柜台边界细碎分片等，若不影响主要功能区的通行组织，保留现有空间信息，不逐项追问精确门位或穷尽连接。证据不足的关系留空，外部核对记录汇总为“本轮不细究的内部细节”；这不表示不相通，也不要求用户逐项确认。
- **确实需要用户判断：**助手复核后仍存在会改变主要可达关系的不同解释，例如功能区唯一出入口、主要检查室连接哪条通道、交通核对外连接哪个片区。只保留这些关键疑点，合并同片区重复问题，提出最少必要问题；不为凑固定数量而增减。

概念关系与门位定位分别处理：能判断可达但不能定位门时，可保存无 `openings` 的 `access`；清晰可见的已有门洞仍记录红点。合理推断不产生虚构门位，也不扩展为交通核或功能块内部所有小房间互通。布局推断说明放外部核对记录，当前问题确需时在MD简述；不给核心JSON增加过程字段。

复核旧清单时，保留原核对号和 S 编号映射，移出的细节项简述处理结果并留存已有答案；剩余问题不重新编号，也不把“无需细究”写成“用户已确认”。所有目标层级的关键疑点解决、名称同步且正式校验和目检通过后，可按该概念精度完成；无需等待非目标内部细节逐一确认。是否足够训练仍由后续模型实验判断。

## 门洞红点与连通关系同步

- 按本轮目标层级检查空间与走廊、相邻空间之间的实际开口，既有清晰门洞继续保留，不因细节项退出提问而删除。清晰门洞记为 `door`，清晰无门开口记为 `open_passage`，近似中心点采用原图像素坐标；不能从空间质心或共墙中点自动生成门位。
- 在对应 `access` 关系的 `openings` 中保存 `id`、`kind`、`position_px`，具体结构见 [schema.md](references/schema.md)。一个空间对的可达关系只保留一条，不同门在同一关系下分别记录，开口 P 编号全图唯一且续作保持稳定。
- SVG 在对应位置绘制实心红点，显示 P 编号；点的标题及属性记录关系编号和两端 S 编号。每个红点必须能回查 JSON 中的开口与空间对，每个已定位开口必须实际画出；名称标签不能遮住红点。
- 半墙未画小门、未见实体分隔的区域连续及有布局依据的概念连接只保存 `access`，可省略 `openings`；无定位红点不等于不相通。不要为满足点数编造位置，也不能因为某处位置不确定而删除其他可辨认门洞。
- 服务窗口仅记 `service`、共墙仅记 `shared_wall`，均不能据此创建人员通行红点。建筑入口继续沿用 E 编号和入口位置标记，不混入室内 P 编号。
- 同步修改 JSON、SVG、MD。MD 概括红点数、对应关系数和未定位的概念连通数。旧样本允许暂缺 `openings`，不因该字段可选就称其已恢复；恢复时须回看本图原图，不借用其他医院的点位。

## 名称是完成条件

先放大原图辨认文字，OCR 仅辅助。名称没有确定时：

1. 保留稳定的 S 编号，名称标为未确认、类型为 `unknown`；SVG 上将该区域标黄并显示“名称未确认”。候选名称不能当作确定名称。
2. 按下节制作完整原图上的编号核对总图和可编辑的名称预估表，默认直接加入现有 `标注说明.md`；每组待确认问题旁必须直接嵌入清晰的局部放大图，让用户在同一 MD 中边看图边填写。用户也可在聊天中按编号确认，只问会影响功能和连通判断的问题。
3. 收到回答后保留用户原名，将其归入共享类别，同步改 JSON、SVG 和 MD，保留已有其他确认。
4. 在所有名称确定前，称为“标注草稿／未完成”，**不能以格式可转换为 GCN 输入、几何检查通过或准备批量标注为理由宣称打标完成**。也不能用猜测或未经确认的“辅助用房”等名称绕过此条件。

用户明确接受较粗的功能名称时，按该名称记录即可。无法确定的名称继续显示在 MD 的未完成清单中；不要求用户补施工细节。

## 核对图与填写

- 房名核对先生成完整原图总图，再为连续片区提供局部图；按图面片区从上到下、同排从左到右排序，边栏引线不交叉。
- 房名固定核对号01、02…写进目标房间内部；连通局部图在各相关房间和走道内写S号或其数字部分，K号只作题号。数字使用高对比底色，避开原字、门扇、开口和红点；狭小空间放大或拆图。
- 现有固定核对号不得重排。局部图、固定映射和确认记录保存在正式样本目录外的持久`临时核对`目录。
- 用户只需在同一MD看局部图并填写；同片区问题集中。详细总图编排、房名表字段与读取规则见[核对细则](references/review-guide.md)。

## 标注说明保持简洁

- MD只留简短状态、空间／关系／开口总数、原图／SVG链接，以及需要用户确认的局部图、问题和填写栏。
- 一题默认“局部图 → 一句问题 → 一句判断 → 我的确认／备注”；解释以足够判断为限。
- 类型明细、操作步骤、校验日志、长篇原理、历史候选和已同步问答退出MD，保存在外部核对记录或归档。完成后只留简短结果和文件链接。
- `summary`只更新自动概览区域；原有答案和图片链接原样保留。旧MD首次迁移默认完整保留，待答案已读取并归档后使用`--compact`精简；不得直接覆盖或删除未同步填写。
- 布局推断的空间对及依据、无需细究的细节记录到外部核对材料；只在确实影响当前确认时给MD补一句必要说明，不向核心JSON添加过程字段。

## 固定记录与完成状态

- 使用外部`review_state.json`保存房名固定号、S号、用户原话和连通状态；`confirmed_connected`、`confirmed_disconnected`、`pending`分别表示已确认连接、不连接和待确认。新项续号；已确认不连接不能再当作遗漏连接反复追问。
- 核对号来自已有映射时先导入，工具遇到旧映射而无新记录会停止，避免静默重新编号。问答、推断和检查记录不进入annotation.json。
- 完成状态分开检查：结构、名称、主要连通复核、图面目检。名称齐全或`valid=true`单独均不代表完成；已明确不连接的节点可以孤立，不为图全连通补边。
- 具体记录字段、命令和更新方式见[核对工具流程](references/review-workflow.md)。

## 核心数据

已确定为庭院、内庭院、室内庭院或挑空的空间均不计面积，无须再问顶盖或可步入属性。读 [schema.md](references/schema.md) 按约定保存 `image`、`spaces`、`relations`。沿用 [space-types.json](references/space-types.json) 的统一功能类别；用户确认的新功能若无法归类，再补充有意义的共用类别，而不是为每个房间单独创造类型。

室内非重叠区域的 `area_ratio` 合计为 1；绿化和庭院／内庭院／室内庭院／挑空空间保留编号和轮廓，不参与归一化。庭院采用 `type: courtyard`、`level: open_space`，无 `area_ratio`；这是本研究的面积统计口径，不表达是否有顶盖或人员可达，连接仍按图面／用户确认独立判断。不保存平方米面积或像素面积字段。入口是关系中的一种，保存入口名称、类型、近似位置和所连空间；不重复维护入口表，也不通过一个“室外总节点”把所有入口互连。

最终 JSON 不保存人工问答、审核日志或推断过程。确认后的事实体现在名称和连接中。未记关系不自动当负样本；原图坐标是标注信息，不能在预测新方案时不加区分地作为已知输入。GCN 训练和 Rhino 执行不在本 Skill 的任务范围内。

## 辅助工具与核验

以下命令中将 `<skill>` 替换为本文件所在目录，`<json>` 为当前样本：

```bash
uv run --with pymupdf --with shapely python <skill>/scripts/annotation_tools.py normalize <json>
uv run --with pymupdf --with shapely python <skill>/scripts/annotation_tools.py render <json> --output <svg>
uv run --with pymupdf --with shapely python <skill>/scripts/annotation_tools.py summary <json> --output <md>
uv run --with pymupdf --with shapely python <skill>/scripts/annotation_tools.py validate <json> --check-dir
```

脚本不识别房名或替用户确认。`questions`按外部固定记录生成带房内数字的局部SVG／PNG，也支持连通问题；总图仍需按核对细则编排并目检。`summary`默认保留填写，`--compact`先归档旧MD再精简。复核时使用`validate --review-state <外部记录> --check-dir`同时报告各项完成状态；不指定记录时只检查结构和名称，不据此宣布完成。

草稿可用`--allow-incomplete`检查结构。退出码1表示错误，2表示名称或指定核对记录尚未完成，0表示所请求检查通过；只有`complete=true`且人工语义、目检一致才定稿。SVG必须实际显示名称、房内编号和已定位红点。

交付前运行正式检查，并渲染 SVG 查看完整图及密集小房间局部，核对可见名称、边界、入口、门洞红点与 JSON 的空间对及坐标一致。`validate --check-dir` 检查红点和 `openings` 的编号、坐标及两端空间对应；它不能替代原图目视判读门洞。检查通过且目标层级的关键疑点已解决后才宣布这张图按概念精度完成；仍待用户判断的关键关系须如实列出。格式检查通过不代表已验证模型泛化或整批样本量充分。

经用户确认的案例事实留在该图数据；有复用价值的判读经验再归纳进规则或共享类别，不把单院特例当成所有图纸的固定规则。
