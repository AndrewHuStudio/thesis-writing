# 四文件与核心 JSON 约定

最终每图目录固定为：具名原图（沿用现有 `编号_项目名称_原图.ext`）、`标注.svg`、`annotation.json`、`标注说明.md`。原图不改动。旧成果在用户指定的本图续作／统一命名范围内迁移，更新当前有效链接，历史备份不改写。

JSON 顶层只有 `image`、`spaces`、`relations`；采用 UTF-8、两个空格缩进。空间具体名称与跨图共享类别分别存为 `name` 和 `type`，中文类别从共享类型表读取，不另存一份可能不同步的中文分类字段。

## image

`file`：同目录原图文件名；`width`、`height`：标注使用的图像像素尺寸。左上原点，x 向右、y 向下。PDF 需先确定单页及工作像素坐标，最终仍保留原始单页 PDF；临时栅格化不新增最终文件。

## spaces

| 字段 | 含义 |
| --- | --- |
| id | 稳定空间编号，同一图内唯一，如 S001 |
| name | 原图可读或用户明确给出的名称；不随意改写用户用词 |
| type | 共用英文功能类别代码，见 space-types.json；其标准中文叫法由同表映射 |
| level | room、open_space、semi_open_space、core_block、functional_block、landscape |
| scope | 功能范围，如 ordinary_outpatient、emergency、public_service；同项目一致 |
| polygon_px | 原图像素多边形，至少三个顶点；不同标注单元不重复占地 |
| area_ratio | 室内占比；各参与统计的非重叠室内区域面积之和为分母。绿化、庭院和挑空空间不保存此字段 |

不保留 `area_m2`、`area_px2`、人工确认记录和施工细节字段。面积可从多边形计算。原图中穿越区域的轴线、家具和铺地图案不自动构成房间隔墙。

本研究将已确定为庭院、内庭院、室内庭院、内院或中厅上空／挑空的区域统一保存为独立空间：`type: courtyard`、`level: open_space`，保留稳定编号、用户名称及轮廓，不保存 `area_ratio`。是否有顶盖或可步入不改变庭院不计面积的统计口径，不再单独追问此属性；普通大厅、候诊区、走道不归入庭院。绿化和 `courtyard` 均不参与室内归一化；调整后重新归一化其余室内空间。庭院是否连通独立依据开口、连续布局或用户确认判断，不由面积排除自动推断。

未确认名称可在草稿中保留 `unknown`，但这会阻止正式完成校验；不得把候选功能当作已确定标签。

## relations

普通关系字段：`id`、`source`、`target`、`type`。

- `access`：空间之间的概念级人员可达。门、无门开口、图面可辨或用户确认的区域连续，以及按 SKILL.md 筛选规则有布局依据的合理推断均可形成该关系。布局推断在 MD 说明，不作为用户已确认；仅共墙或服务窗口不足以建连。不同门连接同一空间对时合并为一条关系，具体门洞／开口分别保存在该关系的 `openings` 列表中。
- `service`：服务窗口／柜台联系，不由此推断人员可穿行。
- `shared_wall`：共墙，不自动表示可达。
- `entrance`：额外保存 `name`、`entrance_type`、`position_px`；`source: null` 表示外部边界接口，`target` 为直接相连室内空间，独立 E 编号。

空间关系按无向概念联系存储，每对空间同一类型只保留一条；不同类型可并存。入口箭头不自动解释为单向权限。外部端点 null 不是供室内寻路的共享室外节点。训练时入口是否转换为特殊节点，由预处理决定。

### access 的可选 openings

清晰可定位的门洞／无门开口应保存近似位置，供 SVG 红点和连通关系互相核对：

```json
{"id":"R001","source":"S001","target":"S002","type":"access",
 "openings":[{"id":"P001","kind":"door","position_px":[100,250]},
             {"id":"P002","kind":"open_passage","position_px":[100,350]}]}
```

每个开口仅有 `id`、`kind`、`position_px`：P 编号全图唯一，续作保持稳定；`kind` 仅为 `door` 或 `open_passage`；位置为原图像素坐标，须有限且在图像范围内。一个空间对可有多个开口，不因此复制 `access` 关系。`openings` 仅用于 `access`，服务窗口和共墙不得附带通行开口。

半墙未画小门、区域连续或有布局依据的概念连接而无可定位门洞时，保留概念级 `access`，省略 `openings`；不得取质心或共墙中点伪造门位。旧样本没有该字段时仍可读取，但不能据此声称已复核全部可见门洞。近似门洞位置是连通关系的定位信息；不保存门宽、门扇构造、半墙缺口形状和内部精确路径。关系存在不表达患者／医护门禁权限，除非另行定义了相应研究任务。无需细究的内部小间若证据不足，可不补关系；未记录不表示不可通行，也不是用户已确认的负例。

## MD 与 SVG

MD只保留简短状态、空间／关系／开口总数、原图／SVG链接和当前待确认问题；每题局部图、短问题、简短判断和确认栏同处。已同步答案、历史候选、类型明细、校验日志与过程说明保存到外部核对材料，归档后退出MD。完成后仅留简短结果和文件链接。`summary`只替换自动概览标记间的内容，保留其余原文；`--compact`须指定外部核对记录并先归档完整旧MD。
SVG 自带原图底图；每个空间都可见“编号＋具体名称＋〔标准功能类别〕”，与 JSON 的 `id`、`name`、`type` 对应，稳定S编号实际置于对应空间轮廓内部。`openings` 中的门洞／无门开口在对应坐标绘制实心红点和 P 编号，标题及 `data-opening-id`、`data-relation-id`、`data-source`、`data-target` 属性对应 JSON，保证双向可查；红点位于空间标签上层。建筑入口沿用 E 编号及独立样式。概念连通没有位置时不强行画红点。名称未确定的区域用显著颜色显示“名称未确认”；用户确认采用 SKILL.md 规定的完整原图框选、边栏标签和引线总图，局部放大图为补充。名称不能仅存在于 SVG 的 title 元素。

核对总图按连续片区自上而下、同排自左向右编排，标签按同一顺序排列，引线不交叉。已有 S 编号保持稳定；房名核对的连续核对号直接写入目标空间内部，图外标签注明同号及S编号。连通局部图在各相关房间和走道内部写S编号或其数字部分，K题号置于标题；只有顶部图例而房内无数字不满足要求。数字避开原字、门扇、开口和红点，必要时拆图放大。对应关系保存在草稿 MD 预估表或外部核对材料中，不加入 `image`、`spaces` 或 `relations`，不影响最终四文件约定。固定映射、确认原话和连通状态保存到样本目录外的review_state.json，不增加核心JSON字段。图片与核对材料按 SKILL.md 放在工作区内、最终样本目录外的可持续保存目录，MD使用可解析的相对图片路径。

## 完成检查

完成需要：名称确定、类别统一、编号／关系有效、多边形有效且不重叠、面积归一化、SVG 可见名称与 JSON 一致、已定位开口与红点一一对应、四文件交付。`validate --check-dir` 额外核对红点编号、坐标、颜色及两端空间，原图中门洞是否判对仍须全图／局部目视检查。按用户原名记载不等于有现场测绘证据；不要作超出当前图纸与用户说明的建筑合规或模型效果承诺。
